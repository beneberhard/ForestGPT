# Methods

## The RAG engine

ForestGPT uses retrieval-augmented generation (RAG) to connect a language model with forestry-specific knowledge. The knowledge base was created through a human-curated conceptual extraction workflow as part of the course Interdisciplinary Project Studies at BOKU University, Vienna, during the winter semester 2025/2026.

Students were divided into seven thematic groups covering the main domains relevant to forest management: (1) silviculture, (2) forest growth and forest growth simulation, (3) forest operations and machinery, (4) forest ecology and biodiversity, (5) climate risks and adaptation A: drought and windthrow, (6) climate risks and adaptation B: pests and pathogens, and (7) policy, regulations, and economics. Each group processed approximately twenty sources. As a guideline, the groups were asked to use about ten textbooks and ten grey-literature sources. Grey literature included lecture notes, teaching material, technical reports, internal documents, project reports, and similar documents that are not usually published through scientific publishers.

The aim was not to produce ordinary summaries, but to extract core concepts and the relationships between them. The students first divided each source into chapters or other meaningful conceptual units. For each unit, they created knowledge cards. A knowledge card was a short text that described important concepts, definitions, processes, and relationships. In addition, the students prepared a structured summary explaining how the concepts of a chapter belong together. To support later knowledge graph construction, they also identified relevant entities and relationships. Entities represented important concepts, objects, processes, or actors. Relationships were expressed as simple subject-predicate-object triplets, for example "thinning - reduces - stand density". This workflow transformed narrative forestry knowledge into a more structured form that could be used by the application.

The resulting text corpus is ingested into the ForestGPT database. The ingestion pipeline accepts PDF, DOCX, TXT, Markdown, CSV, XLSX, and XLSM files. During ingestion, each document is converted to plain text, split into overlapping chunks, and stored together with document metadata. In the current implementation, chunks have a target size of 1200 characters and an overlap of 180 characters. This overlap helps to preserve context across chunk boundaries. The system also stores a file hash and embedding metadata, so that already ingested documents can be skipped and documents can be re-embedded when the embedding model changes.

For retrieval, ForestGPT uses a hybrid retriever. It combines lexical matching with semantic vector similarity. The lexical component is based on BM25, which gives high scores to chunks containing important query terms. The semantic component compares the embedding of the user query with the stored chunk embeddings using cosine similarity. The final retrieval score combines both signals, with a slightly higher weight for BM25 than for vector similarity. This design was chosen because forestry questions often contain precise technical terms, but may also be phrased in more general language. The retriever returns the top-k most relevant chunks, which are then used as evidence in the language-model prompt.

## The growth simulator

The growth simulation component is based on the r3PG package. This simulator was selected because it fits the aim of the ForestGPT prototype: to support stand-level forest management scenarios while keeping the input requirements manageable. In its 3-PGmix version, r3PG can simulate mixed-species stands, multi-cohort stands, and management interventions such as thinning. The model has a relatively simple structure compared with more complex process-based models, and it uses input variables that are often easier to obtain in practical forestry.

This balance was important for the present application. ForestGPT is intended as a field-oriented decision-support prototype. It therefore needs a model that is scientifically credible, but still simple enough to be connected to a user interface for forest managers. The r3PG package provides an implementation of 3-PGpjs and 3-PGmix and exposes the function `run_3PG()`. The model can simulate pure stands as well as stands with several species.

The main ForestGPT backend is written in Python, while r3PG is an R package. Therefore, a Python-to-R bridge was implemented. The Python backend writes the simulation input to JSON, calls an R script through `Rscript`, and reads the JSON output back into the application. One R script prepares the input tables required by r3PG, including site, species, climate, thinning, parameter, size-distribution, and settings tables. A second R script calls `r3PG::run_3PG()` and converts the monthly long-format model output into annual output records. The annual output variables stored in the application include age, stems per hectare, basal area, mean diameter at breast height, mean height, standing volume, aboveground biomass, and mean annual increment.

Because r3PG is a stand-level simulator, it does not initialize uneven-aged stands from individual tree data. As a practical approximation, several cohorts can be defined for the same species. For example, if a user defines three cohorts of different ages for one species, these cohorts can represent an uneven-aged stand grouped into three age classes. This solution keeps the model input simple while still allowing the user to represent more complex stand structures.

For the first ForestGPT implementation, several r3PG settings were fixed as defaults. This was done deliberately, because the application is intended for forest managers and should not expose all technical model parameters. The model is run with the 3-PGmix configuration using `light_model = 2`, `transp_model = 2`, and `phys_model = 2`. These settings activate the mixed-stand version of the model and can also be used for pure stands. The non-linear height model is used (`height_model = 2`), bias correction is activated (`correct_bias = 1`), and d13C calculation is deactivated (`calculate_d13c = 0`). The chosen parameter set follows the Central European parameterization described by Forrester et al. and is currently represented in the application by the metadata values `country = Switzerland` and `region = NULL`. These values are not user inputs, but describe the selected parameter set. Since the parameterization is considered suitable for many Central European forests, it is an appropriate default for this prototype.

r3PG can use many site and climate variables, including latitude, altitude, available soil water, soil class, monthly temperature, precipitation, radiation, and frost days. In the current ForestGPT interface, only a reduced set of expressive site variables is exposed to the user. These include altitude, soil moisture, and site fertility. Soil moisture is used as an intuitive proxy for soil water availability, while site fertility represents general productivity and nutrient status. Other variables are handled internally or set to defaults. This follows the principle of model-internal completeness and user-facing simplicity.

## The geospatial database

The spatial data component of ForestGPT is implemented with PostgreSQL and the PostGIS extension. The database stores stand geometries and related stand information. Example stands were created with QGIS by connecting QGIS directly to the PostgreSQL/PostGIS database. Stand polygons were then drawn in QGIS and saved into the database.

This setup allows the application to display selected stands on a web map and to use spatial attributes as context for the decision-support process. For each stand, the backend can calculate spatial summaries such as geometry type, validity, area, perimeter, centroid, and bounding box. The application can also summarize nearby road data when road layers are available in the database. This includes the nearest road distance, counts of road features within defined buffers, and road length within 250 m and 500 m of the stand. In addition, terrain summaries can be included when raster data are available. These spatial variables are not only displayed to the user; they can also be passed into the language-model prompt as part of the stand context.

## The default value engine

The default value engine was added because forest managers will often not have a complete set of model input parameters available in the field. The application therefore supports two input modes.

In variant A, the user provides species, age, stem number, mean height, and mean diameter at breast height. These values are treated as measured or supplied inventory values and are passed directly into the simulation preprocessing. In variant B, the user provides only species, age, and top height. This second mode is intended for situations where only limited stand information is available.

When variant B is used, missing stand variables are estimated from yield tables. To avoid interpreting yield table values as fully stocked stands for every species, the user also provides the stocking degree of the stand and the proportion of each tree species. The default value engine rounds stand age to the nearest five-year step and filters the yield table for that age. It then identifies the site classes whose top heights bracket the user-provided top height. Linear interpolation is used to estimate effective site class, stem number, mean diameter, mean height, and standing volume. These estimated stand variables are then translated into the initial biomass pools required by r3PG, including stem biomass, root biomass, and foliage biomass. The following years of the simulation are then calculated by the growth simulator.

Out of the twelve tree species calibrated for the selected r3PG parameter set, eight species were implemented in the prototype. The final manuscript should include a table listing these species and the corresponding yield tables used for each of them.

## The GenAI application

The GenAI component of ForestGPT connects four sources of information: the user's question, the selected stand, the simulation output, and the retrieved forestry literature. The language model is therefore not used as a stand-alone source of scientific truth. Instead, it acts as an interpretation layer that receives structured context from the application and converts it into a concise management-oriented answer.

The backend was implemented in Python with FastAPI. FastAPI exposes HTTP endpoints for stand creation, spatial summaries, field observations, simulation runs, document ingestion, document retrieval, and chat interaction. Pydantic models are used for input and output validation, and FastAPI automatically provides OpenAPI documentation for development and testing. During local development the API is served with Uvicorn. The frontend is a Leaflet-based web application displayed on an OpenStreetMap base map. It allows the user to create and select stands, enter simulation inputs, preview default values, run r3PG simulations, inspect output tables and plots, upload documents to the knowledge base, save field observations, and ask questions through the chat interface. An earlier Streamlit interface is kept only as a development helper.

Persistent data are stored in PostgreSQL/PostGIS and accessed through SQLAlchemy. The database stores stand records, geometries, simulation runs, simulation outputs, source documents, document chunks, chat sessions, chat messages, and field observations. Storing these elements in one database makes it possible to combine them when a question is asked. For example, a single answer can use stand geometry, nearby road information, terrain information, recent field notes, growth simulation results, and retrieved literature chunks.

The chat workflow starts when the user asks a question. If the user has selected a stand or simulation run, the corresponding database records are loaded. The system then retrieves the most relevant text chunks from the knowledge base using the hybrid BM25 and vector retriever. At the same time, the backend loads recent conversation memory from the active chat session. In the current implementation, the last four chat messages are included, with long messages shortened before they are inserted into the prompt. This memory is used only to resolve follow-up questions, for example when the user asks "what about thinning?" after an earlier question about a specific stand. If the current question conflicts with the memory, the current question is prioritized.

The prompt is built from several blocks: stand context, simulation summary, recent conversation memory, retrieved literature excerpts, the current manager question, and system instructions. The stand context may include species, age, area, user-defined properties, spatial summaries, nearby road summaries, terrain summaries, and field observations. The simulation summary contains the output of the selected r3PG run. The retrieved literature chunks provide external forestry evidence. The system instructions tell the model to distinguish model output from management recommendations, state assumptions and uncertainty, avoid inventing simulation values or citations, and recommend checking local regulations and qualified local advice for operational decisions. The prompt also allows an explicit structured refusal. If the available stand data, simulation context, conversation memory, and retrieved corpus do not contain enough evidence to answer a question reliably, the model is instructed to answer that it does not know based on the available sources, to state what information is missing, and to describe which additional data or sources would be needed. This was included to reduce plausible-sounding but unsupported responses.

To keep prompts within a manageable size, the backend reduces the number of retrieved chunks if the assembled prompt becomes too long. The prompt is then sent to an OpenAI-compatible language-model client. In the current configuration, the integrated model is `gpt-4.1-mini`, but the architecture can also connect to other OpenAI-compatible endpoints, including local model servers. The maximum response length and model endpoint are controlled through environment variables.

The answer returned by the model is stored in the database together with the user message. The assistant message also stores metadata about the stand, simulation run, and retrieved chunks used for the answer. This creates a traceable record of the information that supported each response. The answer is then returned to the frontend together with the retrieved context and simulation summary.

Document ingestion can be done in two ways. First, documents can be placed manually in the corpus directory and ingested through a backend command. Second, documents can be uploaded directly through the web interface. Uploaded files are checked for supported file type, assigned a safe file name, hashed to avoid duplicate ingestion, converted to text, chunked, embedded, and written to the database. LlamaIndex dependencies are included in the project because the framework may support later extensions of the ingestion and indexing workflow, although the current retrieval implementation is custom and transparent.

The application is deployed locally with Docker Compose. The Compose setup contains two services. The `db` service runs PostgreSQL/PostGIS and stores the spatial and application data in a persistent Docker volume. The `app` service builds the Python application image, installs the required Python and R dependencies, installs the r3PG package in R, and serves the FastAPI backend together with the Leaflet frontend. The application container connects to the database container through the internal Docker network. The `data` and `storage` folders are mounted into the application container so that the document corpus and generated files remain accessible outside the container.

Overall, the prototype follows a modular architecture. FastAPI coordinates the backend, SQLAlchemy and PostGIS store persistent spatial and application data, r3PG supplies the process-based growth simulation, the default value engine translates limited field information into model inputs, the RAG engine links the model to forestry literature, and the LLM produces a readable management answer. This modular design was chosen so that each scientific or technical component can later be improved without rewriting the whole application.

## Code availability and computing environment

The source code is managed with Git and is intended to be made available through a GitHub repository. The final manuscript should report the repository URL and, if possible, the exact commit used for the analysis or prototype demonstration.

The prototype was developed and tested on a local computer. For reproducibility, the final manuscript should report the hardware and software environment used for the main demonstration, including operating system, processor, memory, Docker version, Python version, R version, and the versions of the main packages. The Docker setup reduces differences between local installations, but these details are still useful for documenting the computational environment.
